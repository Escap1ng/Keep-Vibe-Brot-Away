## 一、六个事故

规矩用 R# 连续编号，全文唯一；每条都注明它来自哪个事故。

### 事故 1：把单位错误当成根因交付

现象：用户报告「托盘图标在，桌面圆点不在」。

我的结论（错的）：`settings.json` 里遗留 `dockX=2358` 超出屏幕宽度，圆点画在屏外。我为此写了钳制逻辑、加 6 个单测，并把这段因果讲给了用户。

怎么被推翻：提交前复核数字，发现 `dockX=2251 + 72` 又不越界——同一套代码给出两个矛盾结论，说明**前提有问题**。改用 DPI-aware 的 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` 重测：

```
WinForms AllScreens  → 1707 × 1067   ← DPI 虚拟化后的逻辑值
GetSystemMetrics(0,1) → 2560 × 1600  ← 真实物理像素,DPI 150%
Tauri 落盘的坐标      → 物理像素
```

我拿虚拟化的 1707 去比物理的 2358。`2358 + 72 = 2430 ≤ 2560`，**圆点从来没出过界**，钳制代码在用户机器上是空转。

诚实记录：「圆点看不见」这个现象最终没找到代码级原因（最可能是当时处于面板展开态，`show_panel_mode` 会 `dot.hide()`，或那个实例已退化，重启即恢复）。它没有闭环，我不给它编一个原因。

- **R1**：跨层比较数字前，先确认每一层的单位与坐标系。Windows 上任何几何结论必须来自 DPI-aware 测量——`System.Windows.Forms.Screen` 在未标记 per-monitor aware 的宿主里返回虚拟化逻辑值。
- **R2**：一个假设被它**解释不了的现象**反驳时（比如那个 2251），先解决矛盾，不要先收尾。
- **R3**：结论必须带前后证据。没有实测支撑的因果链写进文档要标「猜测」，不能写「根因」。
- **R4**：允许推翻自己，但必须显式写「已否证」并留下否证它的证据。调试记录里保留被否证的假设，比只留成功路径有价值。

### 事故 2：三轮「重启就好」，而适配器从来没装过

用户连续三次报告「还是无法触发」。我三轮都在改代码：统一指纹口径、拆 `InsertOutcome` 三结局、给 facts 加 in-flight 去重、修预算重复计费。每处改动本身都对，**但没有一处是当时的阻塞点**。

真正的阻塞点是一条 `Test-Path` 就能查出来的事实：

| 取证 | 实测 |
|---|---|
| `events.log` 内最大 ts | 25 小时前——**零事件流入** |
| hook 配置文件（当时的 Trae，两处候选路径） | **都不存在** |
| `projects/` | 两个目录：`C:\Users\...\KVBA` 与 `c:/Users/.../KVBA` |
| `projects/*/` | 都只有 events.log，**没有 facts.json** |
| `budget.json` vs `stats.json` | LLM 用 21 次，今日发卡 1 张 |

完整因果链（每一环独立致命）：

```
hook 从未创建 → 零上报 → 25h 无事件
  → kick_facts 只在事件流入时调用 → facts.json 永远不存在
  → 主题恒为 framework-unknown → 知识分支每次让 LLM 写同一句话
  → 正文指纹与 20min 内那张重复 → Duplicate
  → 用户点「来一道」只看到「刚递过同款内容」,队列永远 0/3
```

- **R5**：**先证明输入到达，再调试流水线。** 任何「没反应」类问题，第一动作是查数据面证据（日志文件、落盘时间戳、对端文件是否存在），不是读代码。这三轮的耗时几乎全部花在一条 `Test-Path` 就能省掉的路上。
- **R6**：区分「代码缺陷」与「现场缺配置」。用户机器上少一个文件比任何逻辑 bug 都更常见，也更难靠读代码发现。
- **R7**：让用户执行「重启一下」前，必须先说清为什么重启会有效、无效时下一步查什么。说了三次「重启就好」而不给判据，等于把排查成本转嫁给用户。
- **R8**：安装类配置要有**一条不经过宿主包装层的自证路径**：直接管道喂 payload 给脚本。「已启用」不等于「能执行」。

（事故 3 就是这条自证路径该救而未救的那一次。）

### 事故 3：hook「已启用」但一次都没执行——坑在我自己写的模板里

配置文件已创建、UI 里已启用，事件仍然为零。逐层排除后，脚本手动喂 payload 正常、KVBA 在跑、端点与 token 有效、JSON 合法且 `matcher:"*"`——唯一断点是宿主的命令拼接：

```
error: unexpected argument 'more\KVBA\adapters\trae-hook\kvba-trae-hook.mjs' found
```

根因：宿主把 hook 命令交给 `trae-sandbox.exe exec --command-line <...>`，命令串里的**内层引号会提前闭合外层引号**，路径在空格处被劈成两半。所以「给路径加引号」这个直觉解法无效，加了照样断；当时唯一稳的写法是路径无空格 + 完全不加引号。

最难看的一条：这个坑是我自己写进 `hooks.sample.json` 的，原文就带内层引号。任何仓库目录含空格（或中文）的用户照抄即中招。该适配器已于 2026-11-09 整体删除，此处只留结论。

- **R9**：示例配置就是产品的一部分。模板里一处错误写法，等于给每个照抄的用户预装一个故障。
- **R10**：诊断分层排除时，先从「脚本自己有没有问题」查起，而不是从链路中段猜。这一步做在前面，范围会立刻从整条链路收窄到宿主拼接层。

### 事故 4：静默吞错与假绿灯

四件事是同一个病的四种长相。

**4.1 落盘失败被吞。** `let _ = std::fs::write(...)` 让 `endpoint.json` 写入失败无声消失，而读取端会回退去读上一次进程留下的陈旧文件——端口属于早已没人监听的旧实例。应用「运行正常」，适配器永远 401，现场看起来一切正常。

**4.2 二值健康指示器。** 设置面板「最近事件」的判据是 `lastEventIn != null → 链路正常`，而这个字段只要落过一条事件就永远非空，于是连续 25 小时显示「链路正常」，把断流完全掩盖。已改为「本次进程摄入 N 条 · 最近 X 分钟前」，显式区分三态：0 条＝适配器未接入 / 有历史但超时静默＝链路曾通后断 / 正常。

**4.3 日志无法证伪。** 当时的 `facts 首版返回不可解析的 JSON(前 240 字)` 把两种**修法完全相反**的故障压成同一句话——「输出被截断」该提上限，「字段类型不符」该改契约；而且只留头部，可截断的判据恰恰只在尾部。单日 `budget.used=52` 里 47 格烧在同一条循环上，47 行失败日志没有一行能回答下一步该做什么。

**4.4 静默兜底造出的假绿灯。** 我当时拿「卡片路径用 800 且成功」当排除传输问题的证据。真相是卡片在契约解析失败时会回填模板文案、照样入队、决策日志照样记 `G7 pass=true 卡片生成并入队`。查 `history.json` 实得：5 张卡里 4 张正文逐字命中模板原文，`optimizedPrompt` 非空 0 次——「不满意→优化提示词」这个闭环从未真正产出过。**我用来做排除证据的那个指标，本身不可证伪。**

真根因（第四轮，有可执行证明）：`llm/providers.rs::sse_lines` 的 `unfold` 状态机每个网络块只吐一行 `data:`，其余压在缓冲区等下一个块；流一结束，残留多行被整坨交给 `serde_json` → 解析失败 → `Err(_) => String::new()` → 静默丢弃。服务器把最后几个 delta 攒进同一个 TCP 写发出是 SSE 常态，于是每次都在 JSON 中间断掉。三条测试在旧实现上两条 FAILED（含跨块多字节字符「框架」→「架」），改成字节缓冲 + 每块排空所有整行 + 尾块按行冲刷后全绿。附带确认：**UTF-8 的 `0x0A` 只可能是行终止符**，按字节切行天然不会劈开汉字。

- **R11**：边界（文件系统、网络、注册表、IPC）失败必须留痕，走统一落盘入口，`log::error!` 带绝对路径 + 影响面。
- **R12**：真相源不要放在可能陈旧的旁路文件里。读不到就显示「未启动」，绝不显示上一次的端口。
- **R13**：不要用 `unwrap_or_default()` 兜底写出「结构正确但内容为空/假」的文件。空文件比不写更难查。
- **R14**：健康指示器必须带计数与新鲜度，不能只有布尔。「曾经成功过一次」不是健康。
- **R15**：诊断信息必须能证伪它自己的至少两个候选假设。判据：一条日志若对所有已知故障形态输出同一句话，它等于没有输出。
- **R16**：打印任何「疑似不完整」的外部输入，长度 + 首 + 尾三者缺一不可。
- **R17**：不要用「另一条路径看起来正常」作排除证据，除非那条路径的成功判据本身可证伪——即能回答「这个成功有没有可能由兜底逻辑产生」。
- **R18**：静默兜底必须自带可观测性。已落地的做法：`AnalysisOut.from_llm` 标记 + 决策日志区分「LLM 出稿 / 模板兜底」+ `Stats.cards_llm / cards_template` 分账 + 设置面板「出稿来源」行；正文被模板回填时来源改判为兜底。
- **R19**：同一份契约的多条调用路径必须共用一个取稿函数。facts 与卡片各写一遍取稿，就会各写一遍上限与错误处理——后来的差异没有任何设计意图，纯属漂移。
- **R20**：改因和加诊断不要混在一次改动里。先只加诊断、跑一轮、让证据选假设，再动手。

### 事故 5：「够不够大」是伪问题，消灭它而不是回答它

第四轮我把 facts 的上限从 400 提到 800 并宣称「与卡片路径对齐」，用户回了一句：**「max_output_tokens 也不够大吧」**。这句是对的，而且它指出的问题比它本身大：只要还存在一个手写上限，「够不够大」就永远是悬案。我在 4 个调用点各写过一个数（400 / 800 / 800 / 240），正是这次错误归因的素材。

照做（调大）还有真实反作用：`max_tokens` 超过 provider 自身硬上限会直接吃 400，故障从「静默截断」升级成「完全不通」。所以"更大"不是更安全，是换个死法。

正确的动作是消灭问题：不下发 `max_tokens`，由 provider 用自己的上限。三家行为不同（OpenAI 兼容 body 不带该字段；Gemini `generationConfig` 不带；Anthropic 强制要求，只能给一个回退值），所以它不是一行改动，而是按 provider 分叉——这个成本值得付，因为它把不可证伪的悬案从代码里物理移除。四处调用点收敛到唯一取值点，并加回归锁 `output_cap_is_left_to_the_provider_not_a_local_number` 防止有人再塞数字。

顺带一条差点踩空的坑：规格写着「单次分析强制 ≤5000 token」，我一度以为删上限就是违反硬约束。想清楚才确认——那约束的是**实际消耗**，而实际消耗由输入侧决定（`system` 约 0.6k + `user` 经 `fit_tokens` 裁到 ≤3.5k），这两处裁剪一行未动。**读规格要读它约束的对象，不能只读数字。**

- **R21**：如果一个参数只是在制造「够不够大」这种无法回答的问题，就删掉它，而不是调它。判据：给出任何值你都没法论证"这个值对"，那这个值本身就是错的抽象。
- **R22**：代码改了，凡是陈述因果的文案都要回扫。`FactsParseErr::Unclosed` 原文案是「输出被 `max_output_tokens` 截断」——上限一旦不再下发，这句话立刻变成新的误导源。注释、断言消息、日志文案、错误提示与被改的代码同属一次提交。
- **R23**：规格里的数字先问它约束什么。「≤5k token」看着像上限，实际约束的是消耗量。

### 事故 6：否定性断言最便宜，也最危险（同一个盲区犯了三次）

- **A：把「我没搜到」写成「它不存在」。** 我断言 `p0ReplaceQueue` 是假开关。实际字段、补丁、替换分支与单测全部存在。错因：拿前端驼峰名 `p0Replace` 去 grep Rust 蛇形字段 `p0_replace_queue`，零命中就下结论。serde 的 `rename_all = "camelCase"` 正是为了让两侧名字不同而存在的。
- **B：把「它存在」写成「它不存在」——通过委托放大。** 我用检索子代理逐条核实 18 项断言，它正确揪出 4 条根本不成立的名字（`dedup_check`、`core.recently_asked`、`capsule:panel-head`、`blake16`），产出质量很高；但同一份产出漏掉了 `p0_replace_queue`，而我因为「前面 17 条都对」就照单全收。
- **C：把「我没查依赖的默认值」写成「它没有这个能力」。** 我断言 `tauri_plugin_log` 没配文件 target，独立运行的 exe 里连 warn 都看不到，并据此提议新增一个 target。实际 `Builder::new()` 的默认 target 就是 `[Stdout, LogDir]`，`%LOCALAPPDATA%\dev.kvba.app\logs\KVBA.log` 一直在写，那 47 次失败全在里面。差一点就交付一处完全无用的改动。真正的病不是「没有日志」，是「没人知道日志在哪」——已把各平台日志路径写进 README，并显式提示它不在 `%APPDATA%` 下。
- **D：第三次犯。** git push 报连不上 `127.0.0.1:33210`，我断言「33210 现在没有监听者」。实际 `uniproxy` 一直在监听。错因：用 `Get-NetTCPConnection -LocalPort 33210 -State Listen` 逐端口扫没命中；换成全量 `-State Listen` 再按 `LocalAddress` 筛就出来了。同一个对象，两种写法，一个漏一个中——而且这次我连"再换一种查法"都没做。
- 同源错误：把用户贴来的 881 行终端转储当成现状叙述。它是历史快照，末尾停在我早已修掉的编译错误上。真正要问的是"现在有没有进程"，一条 `Get-Process` 就够。
- 另一条相邻教训：**"没运行过"和"运行了但没产出"是两件事**。我当时用前者解释了后者，真实现场是后者，原因在门控不在传输（见第四节）。

- **R24**：任何「不存在 / 未实现 / 没有调用点」的断言，必须给出你搜了什么、以及为什么这个搜索足以覆盖。跨语言契约要两侧各查自己的规范名。
- **R25**：下否定性结论前做一次反向确认：直接打开那个文件读那几行。成本 5 秒，比撤回一次结论便宜两个数量级。
- **R26**：子代理的产出不是地面真相，尤其是它的沉默。可作线索来源，但写进文档的每条断言我要能自己复现。
- **R27**：断言某个能力/字段/输出不存在之前，先查依赖 crate 的默认实现；提出「新增 X」之前，先证明「X 现在真的没有」。只看自己这一侧的调用点远远不够。
- **R28**：否定性结论必须换一种查法复验（按条件过滤 vs 全量枚举再筛）。"我再搜一次"要用不同的搜法，否则只是把同一个盲区再看一遍。
- **R29**：区分快照与现状。用户贴来的终端输出、日志文件、转储默认是过去时；描述"当前状态"前重新采一次实时证据。

## 二、环境边界：别把沙箱产物当缺陷修

我这侧的终端跑在沙箱里：工作区之外的路径不可写（`%LOCALAPPDATA%`、`%APPDATA%`、`%TEMP%`），且连不上用户的 `127.0.0.1`——`Invoke-WebRequest` 到 KVBA 端口直接「无法连接到远程服务器」，而 `Get-NetTCPConnection` / `Get-Process` 能看到其他进程，说明只有本机回环连接被隔离。于是会出现：

```
failed to create webview: WebView2 error: 0x800700AA
logging error: 拒绝访问。 (os error 5)
```

这不是应用的问题。判别方法：同一份二进制在用户自有终端里 GUI 正常、只有沙箱内失败 → 环境限制。

- **R30**：永远不要从沙箱里替用户启动 KVBA。那会起一个写不了 `APPDATA` 的残废实例，然后把环境故障当产品缺陷去修。启动一律交给用户自己的终端。这条我曾写下「本轮已避开」，下一轮仍复犯——错因不是不知道规矩，是动手前没读这份文档。
- **R31**：不要在承诺里绕过自己写下的禁令。明知不能起，还因为「用户把选择权交给我」而起，是把便利凌驾于证据之上。
- **R32**：用户侧动作该交回去就交回去，并给可直接粘贴的命令，而不是替他做一件必然失败的版本。
- **R33**：在有热重载的宿主里，每次保存都是一次部署；编译不过就等于对用户 DoS。我连续两轮把用户正在跑的 dev 进程带走（一次 `starts_with` 拼错，一次把函数签名与三处调用点分次保存）。落盘前先 `cargo check`；改跨文件签名时，签名 + 全部调用点 + 受影响测试写进同一次编辑。

沙箱内可以做的：读 `%APPDATA%` 下的取证文件（`decision-log.jsonl`、`events.log`、`budget.json`、`stats.json`、`endpoint.json`）、跑 `cargo` / `npm` 门禁、用管道喂假 payload 验证 hook 脚本的解析与归一化路径。

结论必须分三类，别把后两类写成第一类：**实测确认**（在真实进程/真实窗口上量到）／**沙箱限制**（我这侧跑不了、需用户本机复验：GUI 冒烟、Keyring 真写、端到端事件流、Updater 签名发布）／**静态审计**（只读了代码没执行，例如 CI 编排）。

## 三、铁律（优先于任何新特性）

1. **绝不阻塞 Agent。** 适配器与 hook 失败一律重试后静默丢弃，并以退出码 0 结束。任何让 Agent 卡顿、报错、弹权限的东西一票否决。未处理的 Promise 拒绝会以 1 退出，必须显式兜底。
2. **优雅降级。** LLM 不可用 → 只出模板卡；额度耗尽 → 攒批不硬打（恢复后不追发，这是设计而非缺陷）；端点不可用 → KVBA 本体照常用。
3. **失败要能看见。** 第一节 R11–R18 就是它的配套。
4. **知情度卡必须最后生成。** 它是唯一能让 Agent 反问「项目用什么框架」的卡型，先出就等于抢走真正该递的话。
5. **事件契约与端点发现文件是协议边界。** 新增一个 Coding Agent 不该改动核心，只该写一个能吐这个 schema 的上报脚本。
6. **门控的拒绝原因必须是可执行的。** 写「队列已满或同指纹重复」这种二选一假提示，等同于把用户推进死路；几种结局必须分别陈述，且陈述的是真实发生的那一个。
7. **熔断/冷却的计数口径要区分「这条路径坏了」与「现在没资源」。** 后者不该进冷却，也不该用 WARN 级——我曾把 `[budget-exceeded]` 计入连败，额度刚恢复就被再挡 6 小时。
8. **免预算重试通道只服务「调用成功但解析失败」。** 其余一律上抛；复用错误处理结构时要复用它的语义而不是它的形状，否则预算耗尽时绕穿闸门、白打真实 API。

## 四、可迁移的缺陷模式（已修，按症状归类）

留这一节的唯一用途：下次看到相同症状，能立刻认出是哪一类。

| 模式 | 症状 | 要点 |
|---|---|---|
| 同一判据两处实现 | 门控放行、护栏拒绝；提示写成假二选一 | **一个概念只允许一个函数**；准确的错误信息不等于修复，它只让用户看清自己仍被困着 |
| 身份键不归一化 | 同一项目裂成两个记忆目录，事件窗口与 facts 互相看不见 | 边界处归一化：分隔符、重复斜杠、尾斜杠、Windows 大小写 |
| 补生成动作只挂在事件流上 | Agent 一闲置就永不重试，facts 恒空，退化出恒定文案 | 有状态的补生成要有启动期入口 |
| 派生值是 setup 期快照 | 队列里有卡，popup 永远显示空 | 随共享状态变化的派生值必须 `computed`，否则注释「一次性快照」 |
| 容器级 `serde(default)` 当补丁用 | 任何部分更新都把 model / BaseURL / 预算刷回默认 | 补丁接口要字段级 Optional，「未提交」与「显式清空」在类型上就要能区分 |
| 跨模型契约严格解析 | LLM 少回一个字段或改用蛇形命名就整份作废，退化成空白卡 | 契约要 `default` + `alias` 宽容；空白卡是最坏产物 |
| 重试重复计费 | 最坏一次分析吃 2 格当日额度 | 「预留额度」与「发起请求」拆两步，重试复用已预留那格 |
| 无 in-flight 标记 | 每条事件都白烧一次 LLM 预算 | 幂等靠状态标记，不靠调用频率侥幸 |
| 打分口径不分事件类型 | 纯浏览会话（读 4 个 `.md`）累出 -100，同窗口一次真实大改（+82）被压到阈值以下 | 审查信号只能来自写事件；罚分按「命中过」结算不按「命中几次」结算 |
| 路由先占坑再饿死 | 审查分支不达标就整批拒绝，同时 `events.log` 里躺着 3 条 `turn.ended` | 多分支按优先级依次尝试；不达标必须回落到还有话的分支 |
| 固定候选无轮换 | 本项目永远只出同一主题，被自己的冷却+去重彻底堵死 | 「从固定候选挑一个」只要没有轮换，迟早被去重层挡死 |
| 事件与时间戳分开取 | `id` 与 `ts` 分两次 `Date.now()`，跨毫秒不一致 | 同一事件的时间戳取一次复用 |
| 常驻客户端缓存端点不刷新 | 插件只在启动时读一次 `endpoint.json`，KVBA 后启动就永久 401 | 惰性重读 + 失败即失效；不要把自己的启动顺序假设强加给对端 |
| 并发上下文按名字做键 | opencode 插件 `lastArgs` 以工具名为键，同一工具并发时互相覆盖，上报出错误的文件与 diff | 用调用级 ID（`callID`）做键 |
| Windows 批处理换行与编码 | `dev.cmd` 用 LF + UTF-8 中文注释，cmd.exe 按字节流解析导致指令边界错位，脚本秒退 | 批处理必须 CRLF + 纯 ASCII；换行契约靠 `.gitattributes` 固定，不属于个人本地配置 |
| 批处理里的重定向 | `echo ... >=18` 落在 `if (...)` 块内被当重定向，凭空生成名为 `18` 的文件 | `>` `|` `&` 在括号块内同样生效，不只是行尾 |
| UI 条目重建后改文案 | 托盘「暂停/继续」文案永不翻转 | 改已挂载 UI 项必须持有原条目引用 |
| 所有权移动后才读长度 | `mem::take` 之后取 `.len()`，决策日志里 `events` 恒为 0 | 先取值再移动 |
| 删除语义走成写空串 | `Keyring::set("")` 让用户以为密钥已清，条目其实还在 | 删除要走删除 |
| 文档与实现漂移 | README 写「队列最多 5 张」而实现是 `MAX_PENDING = 3`；README 写「点击穿透」而全仓 `set_ignore_cursor_events` 调用为 0 | 文档只能描述代码做过的事；改常量同批改文档；决定不做要在规格里写明理由 |
| 文档结构大改不回扫 | 删掉小节让插件生效路径变孤岛；引用已删除文档留下断链；文件名拼错导致全站引用带错别字 | 移动/删除/改名文档 = 修改代码，同一次提交内闭环（`git mv` + `grep -i` 复验） |

## 六、给协作者的话

- **先量，再动手。** 最贵的从来不是代码，是我先给了一个错的根因、又连着三次让用户「重启一下」。带单位的观测值比合理的叙事可信；叙事再顺也不能替代一次 `Test-Path`。
- **别为看不见的东西写复杂修复。** 没有证据时该做的是加日志、加量测，让下一次能看见。事故 1 的钳制代码就是反面教材——它正确、有测试，且在用户机器上空转。
- **「够不够大」问不出来就别问了，把那个数字删掉。** 好的收敛方向是让问题消失，不是让答案变大。
- **改代码的那个人负责同步文档与常量。** README 里那句「点击穿透」误导过我整整一轮。
- **动手前先读这份文档，尤其第二节的环境禁令。** 规则存在不等于规则被加载。
- **铁律不是教条，是已经付过学费的地方。** 「绝不阻塞 Agent」每加一个适配器都会被人试着绕过一次。
- 这个项目主要由一个人长期在写。**注释要写给三周后完全忘了上下文的你。**
