# KVBA 规格书评审意见(聊聊我的看法)

对 [InitPrompt.md](./InitPrompt.md) 进行整体评审。结论先行:**这是一份质量明显高于平均水平的任务书**——产品定位锋利、成本控制是"结构性"的而非口号、里程碑切分合理。可以按此开工。但有 5 个真实风险点和约 8 处规格缺口,建议在 M1/M2 动手前先拍板,否则会在胶囊交互、事件摄入两处返工。

## 总体评价

1. **问题定义诚实且锋利**。"氛围编程脑腐"不是造词焦虑,而是真实发生的认知衰退:执行权转移后,审查能力和项目知情度随之流失。KVBA 选择站在"认知"一侧而不是"执行"一侧,这个生态位目前没有竞品,定位成立。
2. **"消费驱动"是正确的反骚扰设计**。pending ≤3、队列满则一切静默、零 LLM 调用——这保证了产品永远不会变成弹窗广告。大多数同类工具死在这里。
3. **成本控制靠结构,不靠自觉**。G1-G7 门控是纯函数、0 token、强制单测;单次分析 ≤5k token 且按字段截断;facts 只在"消费 ≥20 次或会话结束"时精炼。这些是硬约束,不是"尽量省"。这是全篇最值钱的设计。
4. **"不满意 → 优化提示词 → 剪贴板 + next-prompt.md"是全产品的杀手闭环**。它把用户的不满转化为可直接粘贴回 Agent 的动作,使"提问"不止于测验,而是真实影响下一轮产出。
5. **非侵入细节懂行**。置顶但不抢焦点(`set_focus` 仅在用户点击后)、idle 态点击穿透、隐藏可退化为托盘图标、系统通知仅兜底——这些正是悬浮助手类产品的全部失败模式,规格都点名了。

## 风险与挑战(按严重度排序)

### R1. 点击穿透与悬停恢复存在逻辑悖论(§9.2,M6 最大难点)

规格要求:胶囊 idle 贴边时 `set_ignore_cursor_events(true)`,用户"靠近(悬停检测)"再恢复交互。但**窗口一旦忽略光标事件,就收不到自己的悬停事件**——这是一个自锁。可行的解法只有两条:

- Rust 侧定时轮询光标位置(如每 100ms,Windows `GetCursorPos`),进入热区才放开穿透;
- 或只对"非交互区"穿透,保留一条细感应边。

规格必须二选一并写明,否则 M6 会卡住。我建议前者(轮询 + 热区),实现简单、跨平台一致。

### R2. 单窗口变形 vs 多窗口的架构抉择未定(§9.1)

胶囊(36px 圆点)→ 横幅(320px)→ 队列弹层 → 设置/历史,如果用多个 WebView 窗口,Windows 上每个 webview 内存开销可观,且透明无边框窗口 resize 易闪烁;**单个 always-on-top 窗口内部变形**则内存最省但要处理尺寸/位置动画。规格 §11 要求稳态 <100MB,多窗口方案有超标风险。建议:**主胶囊窗口单实例变形承载全部三态,设置/历史用独立小窗口用完即关**。这应写入 M1 的决定。

### R3. 适配器提取 diff 的工作量被低估(§4.1)

Claude Code hooks 的 payload 只给 `tool_input`/`tool_response`,**不含 diff**。归一化 schema 里的 `diffHead`、`lineDelta`、"删除被依赖文件"等字段,需要 bridge 自行执行 `git diff`/解析工具输出才能算出。这部分是 M2 里最重的活,规格只字未提提取算法。JSONL 兜底方案(方案 C)还依赖非稳定的转录格式,应明确其为"尽力而为"降级源。

### R4. G5-A 的信号启发式跨语言不可靠(§6)

"新增异常路径未包 try/catch"、"注释密度骤降"这类判断要纯 Rust 实现,面对 JS/TS/Python/Rust 混合项目误报率会很高。建议:**G5-A 只做保守的文本级信号**(行数、URL/http 关键词、TODO/FIXME、裸 throw),语言级语义判断交给 G7 的 LLM 一次性完成——反正那才是允许花 token 的地方。

### R5. 成功度量无法自证(§1.5)

"提示词被粘回比例 >30%" 在不启用反向代理模式的前提下**根本测不到**;回答率 >60% 也需要本地埋点。建议增加一个本地 `stats.json`(回答率、跳过率、各主题通过率),否则两周后的"成功验证"无从谈起。这不违背纯本机原则。

## 规格缺口(建议动手前补全)

1. **前端框架自相矛盾**:§10 建议 Vue3+Vite+TS,组件命名却写 `Capsule.tsx`(React 惯例)。必须先定框架,直接影响 M1 脚手架。
2. **评估时机未定义**:G1-G7 由谁触发?规格只有 `gate_tick()` 手动按钮。应明确:事件摄入后去抖(如 3s)自动评估一次。
3. **HTTP 端口/配对发现机制缺失**:适配器如何知道 `<port>` 和首个握手 token?建议主程序启动时写 `<dataDir>/runtime.json`(端口 + 配对码),适配器读取后走 `/kvba/hello` 换事件 token。
4. **"攒批"降级没有出口**:每日额度耗尽后"只累计信号不调 LLM",但攒的批何时消费?建议:次日额度重置后优先消费一次合并批。
5. **无 API Key 的冷启动体验未定义**:没有 Key 时产品完全静默(所有卡片都走 G7)。应在托盘/胶囊给出"请先配置模型"的引导态,否则用户以为程序死了。
6. **HKDF salt 存放位置未写明**:建议 `<dataDir>/salt`,并在文档中诚实说明其防护边界(防随意翻看,不防本机管理员)。
7. **哈希算法混用**:事件 id 与 G6 用 blake3、项目目录用 sha256。可以接受,但建议统一声明:文件系统路径命名用 sha256(兼容性好),其余身份哈希一律 blake3。
8. **面板"失焦自动收起"与非置顶的关系**:非置顶面板会被 IDE 盖住,需确认这是预期行为。

## 建议的决策(若开工,按此执行)

- 框架:Vue3 + Vite + TS(尊重规格建议,组件名改 `.vue`),或改 React+TSX 与命名一致——二选一即可,我倾向保持 Vue3(规格原意)。
- 窗口形态:单胶囊窗口变形(三态)+ 按需设置窗口;点击穿透采用"光标轮询 + 热区"恢复机制。
- 门控信号:G5-A 保守化,语义判断下沉到 G7 LLM。
- Provider:三实现照做,但优先把 openai-compatible 打磨完整(它可通过中转站覆盖另外两家,是保底路径)。
- 补一个 `stats.json` 本地统计,支撑 §1.5 验收。
